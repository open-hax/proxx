Exactly: schemas guarantee “enough structure to mean something,” protocols guarantee “enough behavior to be usable,” and anything extra is just gravy.

Let’s port that frame into Proxx’s policy engine. I’ll keep it tight and we can zoom into any part you pick.

## 1. Decide the core policy questions

For Proxx, a policy contract is answering things like:

- “Is this operation allowed?” (e.g. `can-call-provider?`, `can-use-account?`)  
- “How should conflicting sources be resolved?” (priority, overrides)  
- “What parameters (limits, scopes, rate‑limits) apply?”

So each policy needs:

- A **kind**: `:contract/kind :policy`.  
- An **id**: namespaced keyword.  
- A **context schema**: what the decision function sees, e.g.:

  ```clojure
  ;; sketch
  [:map
   [:actor/id :string]
   [:org/id :string]
   [:provider/id :keyword]
   [:operation [:enum :call :list :inspect]]
   [:inputs any?]]
  ```

- A **decision expression or fn reference**: your DSL or SCI code.  
- Optional **priority / store / policies** from `contract/base`. 
Can you write (in your own words) the minimal context map you want every Proxx policy to see?

## 2. Malli: base + policy overlay

Apply the same base‑plus‑overlay pattern:

- Base (already sketched earlier):

  ```clojure
  (def contract-base-schema
    [:map
     [:contract/kind keyword?]
     [:contract/id keyword?]
     [:contract/priority :int]
     [:contract/store [:enum :sql :edn :json :yaml :mongodb :redis :in-memory]]
     [:contract/context any?]
     [:contract/policies [:sequential :policy/id]]])
  ```

- Policy‑specific overlay:

  ```clojure
  (def policy-schema
    [:map
     [:contract/kind [:= :policy]]
     [:policy/effect [:enum :allow :deny :observe]]
     [:policy/mode   [:enum :hard :soft]]         ;; hard = blocking, soft = advisory
     [:policy/expr   expr-schema]                 ;; your EDN DSL
     [:policy/context-schema malli-schema-ref]])  ;; shape of ctx at decision time
  ```

- Policy contract = `[:merge contract-base-schema policy-schema]`.  
  That gives you “inheritance” without OO.

## 3. Protocols: what the policy engine calls

Define a minimal protocol the engine depends on:

```clojure
(defprotocol Policy
  (policy-ctx-schema [policy])
  (policy-decision   [policy ctx])   ;; returns {:effect :allow/:deny/:observe, ...}
  (policy-priority   [policy]))      ;; includes base + overrides
```

Implement it generically for maps:

```clojure
(extend-protocol Policy
  clojure.lang.IPersistentMap
  (policy-ctx-schema [p]
    (:policy/context-schema p))

  (policy-decision [p ctx]
    ;; assume ctx is already validated against policy-ctx-schema
    (eval-expr ctx (:policy/expr p)))   ;; your interpreter returns an effect map

  (policy-priority [p]
    (get-effective-priority p))         ;; from ContractBase
)
```

The **policy engine** now only knows how to:

- Take a **set of policy maps**.  
- For a given `ctx`, run `policy-decision` over each, sorted by `policy-priority`.  
- Combine results according to some conflict strategy (deny‑wins, last‑writer‑wins, etc.). 
No inheritance anywhere, just maps + schemas + protocols.

## 4. Glue to concrete Proxx use-cases

You sketched kinds like `:provider`, `:account`, `:strategy`, etc. Use policies to govern them:

- A **provider‑policy** contract might say:  
  “Actor with role X can call provider P with model family M, but only up to N tokens per minute.”

  Its `:policy/context-schema` would include `:provider/id`, `:model/id`, `:usage/last-minute`, etc., and `:policy/expr` would encode that logic in your DSL. 
- A **routing‑policy** contract might say:  
  “For this tenant, prefer provider A, fallback to B, but never use C.”

  Its context schema would include tenant, requested capability, maybe cost. The interpreter yields a decision structure the routing layer understands (e.g. ordered list of providers + constraints). 
So, concretely, your Proxx router becomes:

1. Build a **policy context** for the decision (who, what, where, load, quotas).  
2. Fetch all relevant contracts `where :contract/kind :policy` matching this context (by org, tenant, scope).  
3. Validate each policy map with Malli.  
4. Run the policy protocol over those maps to get a composite decision.
